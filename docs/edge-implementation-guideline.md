# LM-IDNet edge implementation guideline

The smallest defensible deployment claim for LM-IDNet is “validated for local anomaly inference on a Linux edge gateway.” The claim should name the hardware, operating system, and workload on which it was verified. The project already contains the essential scoring logic. The remaining work is mainly packaging, controlling resource use, and demonstrating that the application runs within the target device’s limits. This guideline describes that minimum implementation; it does not imply that edge deployment has already been validated.

The starting point is the existing [`score_window()` function](../src/lm_idnet/models/scoring_stage.py). It scores one prepared window without reading or writing external state. Training and calibration can remain on a development machine, with the resulting model and threshold copied onto the gateway. The deployment command should reuse the existing artifact validation, including the check that the threshold belongs to the loaded model, and initialize the likelihood backend once. For the minimum deployment, keep adaptation in `static` mode. Running inference at the edge does not require training there. Retaining Python, NumPy, and SciPy is reasonable until measurements show that the chosen gateway cannot support them; SciPy is still used in the complete anomaly score even when the likelihood backend is LM.

The main application change should be one small deployment command that loads those artifacts once, accepts one validated `WindowRecord` at a time, calls `score_window()`, and immediately emits the result as a JSON line. A stream of JSON lines on standard input and standard output is sufficient for this interface. Preserve the configured category order and trained window duration, and retain the distinction between an observed silent window and missing capture coverage. The current research runner in [`scoring_stage.py`](../src/lm_idnet/models/scoring_stage.py) loads complete processed captures and accumulates every result in memory. The deployment command should keep only the model, threshold, and current window in memory rather than retaining the history of results.

Accepting prepared windows from an existing local collector is the shortest implementation. In that case, describe the supported scope as edge inference on supplied windows. If LM-IDNet itself must monitor live packets, it also needs an incremental window counter. [`PacketTransformer.build_time_series()`](../src/lm_idnet/processing/packet_transformer.py) currently collects all packet records before constructing a DataFrame, so it is unsuitable for an indefinitely growing input stream. A live counter should retain the category counts for the active window, emit a completed window at the configured boundary, and reset the counts. It must preserve the existing packet classification, device filtering, UTC window boundaries, and coverage semantics. The research preprocessing path can remain available for offline experiments.

The deployment image should compile the native LM library during the image build and launch the application directly at runtime. The current [`docker-entrypoint.sh`](../scripts/docker-entrypoint.sh) recompiles the library at every startup, although the [`Dockerfile`](../Dockerfile) already compiles it during the build. Move compilation entirely into the build and remove the startup compilation requirement. Deployment should launch a prepared image without rebuilding it or downloading dependencies; the existing [`run.sh`](../scripts/run.sh), which invokes an image build before execution, can remain a development runner. Install the application without the test extra in the deployment image. Build and verify the native library for the gateway’s actual architecture. Docker packaging alone does not establish ARM compatibility, because container code must match the host architecture. [Docker’s multi-platform build documentation](https://docs.docker.com/build/building/multi-platform/) explains the available build options.

The decisive validation is a benchmark on the actual gateway. The current [backend benchmark report](../reports/D-LinkDayCam5/lm_backend_benchmark.json) records roughly 12 microseconds for a representative LM score on an x86 development host. That measurement covers the numerical scoring call and does not establish complete deployment latency or memory consumption. The local `feature/volume-anomaly` branch already contains a small `benchmark_scoring()` implementation in `src/lm_idnet/evaluation/benchmark_stage.py`; reuse its timing, process-memory, and artifact-size measurements where applicable rather than creating another benchmarking framework. Its existing reports describe development-host measurements and must not be presented as target-device validation.

On the target device, record the hardware, operating system, application revision, dependency versions, input workload, and window duration alongside startup time, complete window-to-result latency, throughput, CPU consumption, and peak process memory. Measure the full Python process rather than only the serialized model size. Replay a representative workload long enough to check that memory and storage do not keep growing, with event and log retention explicitly bounded. Include packet collection and aggregation if the deployment claim covers them. Evaluate these results against the target’s available resources and required processing rate. Keep processing latency separate from the waiting time imposed by the configured window duration: fast scoring after a ten-minute window closes does not imply immediate attack detection.

For basic unattended operation, use one ordinary service configuration with automatic restart and bounded logs or event output. Verify that inference continues without internet access and that a restart reloads the validated model and threshold. A small integration check should demonstrate that the deployment command produces the same scores and decisions as the existing scorer on the same windows, while preserving validation failures for malformed inputs and incompatible artifacts. Static inference avoids the additional persistence and refit requirements of adaptive operation; validate those separately if adaptive edge deployment becomes part of the claim.

After implementing and measuring this path, the supported statement can be written as: “LM-IDNet supports local inference on [device and operating system], processing [workload] within [measured latency and memory limits], with bounded runtime state and no internet dependency during inference.” Fill those placeholders with observed results and state whether input windows are supplied by a collector or generated locally from packets. Until target-device measurements exist, “edge-oriented prototype” is the wording supported by the current evidence.

The project has progressed far enough to justify a controlled static edge pilot. Its numerical backend, training, calibration, and individual-window scoring are already implemented. Deployment packaging, service startup, logging, and hardware benchmarks can be developed separately and remain useful as the detector improves. The greatest risk of rework is the interface between packet collection, model artifacts, and scoring. Stabilising that interface before implementing the live runner is the nearest useful step.

The separation should remain simple: research produces a model and threshold, and the edge application loads them and calls the same `score_window()` used by the research pipeline. Improvements to parameter fitting or calibration would then produce new artifacts without requiring changes to the deployment runner, provided the input and scoring contract remains compatible. Keep this within the existing package. A separate implementation of the detector would create two versions to maintain. Some detector changes will still require runtime changes, so this separation reduces rework without promising that every future feature can be deployed without modifying code.

Before building a live packet collector, decide which detector will be deployed. The current branch consumes four protocol counts, while `feature/volume-anomaly` introduces packet behaviour measurements, direction parameters, and different threshold and event formats. A collector written around today's four-count input would need changes if those additions are adopted. Packaging and hardware experiments can start now, but settling the selected feature format first will reduce rework in ingestion and scoring. Unfinished work on unrelated research outputs, such as forecasting, need not block a static inference pilot.

The nearest concrete compatibility fix is to bind the model to its input semantics. During this assessment, a synthetic model saved under a ten-minute configuration was accepted under a five-minute configuration with the same fingerprint. [`ModelArtifact`](../src/lm_idnet/models/schemas.py) does not record window duration, and the loader cannot check it. Store the trained window duration and relevant packet-filtering semantics with the model, include the input contract in compatibility checks, and reject incompatible input windows. Once artifacts will move between deployed software revisions, an explicit format version is sufficient; a migration framework can wait.

The next fix is a small shared loading function for inference. Currently, [`load_model()`](../src/lm_idnet/artifacts.py) requires the full research configuration and compares training-capture identifiers. The gateway should need artifact paths and the expected device and input contract. Reuse `load_artifact()` and centralise the model–threshold compatibility checks so the research runner and edge runner enforce the same rules. Retain training identifiers as provenance without requiring a live inference command to declare research partitions. This keeps future artifact changes concentrated in one place.

Small validation gaps should also be closed before deployment. Training checks the processed dataset's device identity, but calibration and scoring do not make the equivalent check. Add those checks at their shared loading boundaries. The threshold schema should reject non-finite threshold values immediately. These are inexpensive correctness fixes that strengthen both the research system and the deployment path.

For the model that will actually be deployed, the nearest research fix is the timestamp and overlap validation already developed on `feature/temporal-model`. The [project report](lm_idnet_full_project_report.tex) identifies overlapping D-Link fitting captures. Resolve that issue and rerun training and calibration before treating those artifacts as deployment candidates. Temporal validation can change the learned model without changing a correctly separated edge runner. Adaptive deployment needs further work because its acceptance policy and restart persistence remain unsettled; static inference is the smallest useful starting point.

The existing focused checks for training, calibration, artifacts, and scoring passed during this assessment: `python -m pytest -q tests/test_scoring_stage.py tests/test_artifact_schemas.py tests/test_calibration_stage.py tests/test_modeling_stage.py` reported 54 passing tests. This supports reusing the existing core, while the compatibility gap above shows that the current checks do not establish a complete deployment contract. Stabilise the input contract and shared loader first, then implement the thin edge runner and the target-device validation described earlier.
